## 1. What This Project Is

A farmer-facing web app for managing farms, fields, and crops, with four AI-labeled features (with Plant Vision now backed by the integrated V2 CNN for Corn/Potato, while the other external AI/LLM providers remain mock): an AI Crop Advisor, Plant Vision (disease detection), a Farm Risk Engine, a Recommendation Engine, and an AI Farm Copilot (conversational). Weather data is also served by a mock provider. Every mock output is explicitly labeled `is_mock: true` in API responses and in the UI — this is a deliberate, tested product principle, not an oversight.

**Plant Vision is now powered by the integrated V2-alpha CNN service for Corn/Potato.** The legacy V1 model is retained only as an archive/reference. See the V2 ML documentation and current Plant Vision service.

## 4. Important Bugs Fixed / Architectural Decisions (Verified Current)

### 4.1 Weather context never reached the AI Crop Advisor
**Problem:** `CropIntelligenceInput.weather_context` was always `None`, even though live weather data existed.
**Fix:** `ai_crop_intelligence.py` endpoint now calls `get_weather_for_field()` and populates it; failures degrade gracefully (prediction still proceeds without weather).
**Files:** `app/api/v1/endpoints/ai_crop_intelligence.py`, `app/ai/mock_crop_intelligence.py`
**Status:** Verified present in current code; covered by `test_crop_intelligence_uses_real_weather_context`.

### 4.2 Rotation history never used
**Fix:** Endpoint now queries the field's own harvested crop history (up to 5) and passes it as `rotation_history`.
**Status:** Verified present; covered by `test_crop_intelligence_uses_field_rotation_history`.

### 4.3 Risk Engine only checked one rare weather flag
**Fix:** Added real threshold-based checks (heat stress ≥38°C, waterlogging ≥25mm + poor drainage/flood, moisture stress ≤3mm + rainfed, humidity ≥75%) in `risk_engine.py`.
**Status:** Verified present.

### 4.4 Weather-risk deduplication collision (`signal_key`)
**Problem:** Multiple simultaneous weather risks (heat + waterlogging + humidity) all shared `risk_type=WEATHER`, so the upsert dedup key couldn't tell them apart — the second one silently overwrote the first.
**Fix:** Added `AIRisk.signal_key` column (migration `b85fbd724fc1`), each weather sub-condition gets its own key.
**Status:** Verified present; migration applied; covered by dedicated tests confirming 3 concurrent findings coexist.

### 4.5 Planting never recorded as an activity → false/missing Activity-Gap risk
**Problem:** Crops created with a `planting_date` had no corresponding `CropActivity`, so the Risk Engine's activity-gap reference point was inconsistent, and crops created through the (then-existing) UI form (which didn't collect a planting date) could never trigger the check at all.
**Fix:** `create_crop` endpoint now auto-logs a `PLANTING` `CropActivity` when `planting_date` is set.
**Status:** Verified present; covered by tests proving both "fresh planting doesn't false-positive" and "genuinely stale planting still triggers."

### 4.6 Validation error 500 crash (Pydantic `ValueError` in a `field_validator`)
**Problem:** `error_handlers.py`'s validation handler passed `exc.errors()` directly to `JSONResponse`, but Pydantic v2 can embed a raw exception object in the error `ctx`, which isn't JSON-serializable — this caused a 500 instead of a clean 422 for certain validation failures (discovered via the new `initial_crop_types` validator).
**Fix:** Wrapped with `fastapi.encoders.jsonable_encoder`.
**Status:** Verified present in current code (`app/core/error_handlers.py`).

### 4.7 Cross-tenant recommendation overwrite (critical, now fixed)
**Problem:** `_upsert_recommendation`'s dedup key was `(crop_id, category, status)` — no `farmer_id`, no `field_id`. Since every field-level risk (DATA_QUALITY, all WEATHER findings) has `crop_id=None`, one farmer's risk scan could silently find and **overwrite a different farmer's recommendation row**. Confirmed live against real PostgreSQL before the fix (Farmer B's scan overwrote Farmer A's unrelated recommendation).
**Fix:** Added `farmer_id` and `field_id` to the dedup filter in `recommendation_engine.py`.
**Status:** Verified present; this is the single most important security fix in the project's history. Covered by `test_cross_tenant_recommendation_isolation_with_same_category_field_level_risk` and `test_two_fields_same_farmer_do_not_collide_on_field_level_recommendation`.

### 4.8 Field creation with initial crops (feature, not just a bug fix)
**Design decision:** Rather than accepting raw `crop_id`s to "attach" (which would require crops to be reassignable across fields — they aren't; `Crop.field_id` is `NOT NULL` + `CASCADE`), the API accepts `initial_crop_types: list[str]` and creates brand-new `Crop` rows scoped to the new field. This eliminates any cross-tenant attachment vector by construction.
**Status:** Backend verified present and tested. **Frontend UI for this is missing — see Section 3.**

### 4.9 Weather-specific recommendation text (UX fix)
**Problem:** All weather sub-conditions mapped to one generic "adjust your irrigation plan" recommendation, and a session-level `autoflush=False` bug meant 3 simultaneous conditions produced 3 duplicate copies of that same generic text instead of one accurate one per condition.
**Fix:** Added explicit `db.flush()` after each upsert; mapped each weather `signal_key` to its own accurate category/text (heat→CROP_HEALTH, waterlogging/moisture→IRRIGATION, humidity→DISEASE_PREVENTION, extreme_alert→RISK_ALERT).
**Status:** Verified present.

## 5. Architecture Summary

**Backend layout** (`apps/api/app/`):
- `models/` — SQLAlchemy models: `user.py` (User/Farmer/Admin), `farm.py` (Farm/Field), `crop.py` (Crop/CropActivity), `health.py` (CropHealthRecord/DiseaseDetection), `ai.py` (AIPrediction/AIRisk/AIRecommendation), `system.py` (Notification/WeatherSnapshot/FarmTimelineEvent/AuditLog), `copilot.py` (CopilotConversation/CopilotMessage)
- `schemas/` — Pydantic request/response models, one file per domain
- `api/v1/endpoints/` — one router file per resource (auth, farms, fields, crops, dashboard, ai_crop_intelligence, ai_plant_vision, weather, risk, recommendations, copilot)
- `services/` — business logic: `risk_engine.py`, `recommendation_engine.py`, `weather_service.py`, `copilot_context.py`, `copilot_service.py`, `storage.py`
- `ai/` — the mock-provider contract layer: `contracts.py` (dataclasses), `base.py` (abstract interfaces), `mock_*.py` (implementations), `factory.py` (selects mock vs. real based on settings — `real` currently raises `NotImplementedError`)
- `core/` — `config.py` (Settings), `security.py` (JWT/bcrypt), `deps.py` (auth dependencies: `require_farmer`, `require_admin`), `error_handlers.py`

**Frontend layout** (`apps/web/src/`):
- `app/` — Next.js App Router pages: `(auth)/login`, `(auth)/register`, `dashboard`, `farms`, `farms/[farmId]`, `farms/[farmId]/fields/[fieldId]`, `.../crops/[cropId]`, `copilot`
- `components/ui/` — design system primitives: `Button.tsx`, `Card.tsx`, `Input.tsx`, `States.tsx`
- `components/AppShell.tsx` — sidebar/nav shell wrapping authenticated pages
- `context/AuthContext.tsx` — auth state, token storage
- `lib/api.ts` — typed fetch client, `lib/types.ts` — shared TS types

**Database:** PostgreSQL, 17 tables, single-head migration chain (see Section 6).

## 7. Development Rules That Must Not Be Broken

1. **Never accept raw `crop_id`s to attach to a field.** Crops are permanently owned by one field (`NOT NULL` + `CASCADE` FK). The `initial_crop_types` pattern (create new rows) is the correct, safe design — don't "fix" it into ID-based attachment.
2. **Every AI/weather-generating capability must stay behind its mock/real factory pattern** (`app/ai/factory.py`). Never wire in a real provider without also gating it behind `AI_MODE`/`WEATHER_PROVIDER`/`COPILOT_PROVIDER` settings, and never claim a mock result is real (`is_mock` must always be accurate).
3. **Any query that upserts based on a computed key must include every dimension that distinguishes tenants/entities** — this is exactly the class of bug in Section 4.4 and 4.7. When adding a new upsert-style dedup pattern, ask "could two different farmers/fields/signals collide on this key?"
4. **Ownership checks belong in the endpoint layer, chained through the full FK path** (Crop→Field→Farm→Farmer), never trusting a client-supplied ID alone. This pattern is consistent across every endpoint — follow it for new ones.
5. **Schema changes require an Alembic migration** (`alembic revision --autogenerate`, then hand-verify — Postgres enum value additions are NOT autodetected and must be hand-written as `ALTER TYPE ... ADD VALUE` inside `autocommit_block()`).
6. **The test database connection is hardcoded in `conftest.py`**, not read from `.env` — this is intentional (never accidentally point tests at a real database).
7. **Don't weaken tests to make them pass.** Every fix in Section 4 was found and confirmed via a failing test or a live reproduction against real PostgreSQL before being fixed — that discipline should continue.
